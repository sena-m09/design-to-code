# image-to-code

デザインカンプの画像を、対象プロジェクトの規約に沿ってコードに実装し、画像との見た目差分が収まるまで調整するスキル。実装の規約・トークン・コマンドはこのスキルに持たせず、対象プロジェクトから読む。

手順の順番、検証と差分の合否、調整の回数、調整を戻すかどうかは `design-flow` コマンドが決める。このスキルに書いてあるのは、`design-flow` に任された手順の進め方だけになる。`design-flow`・`design-image`・`figma-diff` は design-to-code リポジトリのコマンドで、`PATH` にある前提とする。見つからなければ、design-to-code の README の導入手順をユーザーに案内する。

## 前提チェック（毎回最初に実行）

次の項目を読む。見つからない項目は推測で埋めず、始める前にユーザーに聞く。

| 項目 | 読む場所 |
| --- | --- |
| 実装規約（マークアップ・CSS・命名・ファイル配置・ブランチ運用） | プロジェクトの規約。エージェントに読み込まれている指示のほか、README と既存コードの書き方も見る |
| lint・型チェック・ビルドのコマンド | `package.json` の `scripts`、プロジェクトの規約 |
| デザイントークンと共通コンポーネント | プロジェクトの規約の記述。無ければ CSS 変数・Tailwind の `@theme`・theme 設定ファイル・デザインシステムのパッケージを探す |
| 描画先の URL と対象セレクタ | プロジェクトの規約、`package.json`。開発サーバーが起動していなければユーザーに起動を頼む |
| 設計幅（CSS px） | 依頼文。書かれていなければユーザーに聞く。スマートフォン向けなら 375、PC 向けなら 1440 などが多い |

設計幅が分かったら、倍率を確かめる。`warning` が出たら、設計幅か書き出し倍率をユーザーに確かめる。

```sh
design-image info <カンプの PNG> --design-width <設計幅>
```

JPG のときは、先に `sips -s format png <カンプ.jpg> --out <カンプ.png>` で PNG に変換しておく。

1 回の実行で実装するのは、画像 1 枚に写っている範囲とする。

## 始め方

プロジェクトルートで、フローを始める。`--check` には、lint・型チェック（ビルドが必要なプロジェクトならビルドも）のコマンドを 1 つずつ渡す。`--tag` には、ユーザーから指定された名前（試している仮説など）を渡し、指定が無ければ省く。

```sh
design-flow start --figma <カンプの PNG> --url <描画先の URL> --selector "<対象セレクタ>" --width <設計幅> --check "<lint のコマンド>" --check "<型チェックのコマンド>"
```

固定ヘッダーのようにカンプに無い要素が写り込む場合は、`--hide "<そのセレクタ>"` を足す。

## 進め方

`design-flow` が返す JSON（以下 directive）に従って、`step` が `done` になるまで次を繰り返す。

1. directive の `owner` が `engine` なら、`command` をそのまま実行する。`cd` や `&&` を前に付けずに単独で実行する（サンドボックスの除外ルールに一致させるため）。
2. `owner` が `llm` なら、`guide` が指すこのファイルの節に沿って作業し、終わったら `report` のコマンドを実行する。
3. どちらのコマンドも、次の directive を返す。迷ったら `design-flow next` で今の手順を確かめる。

`report` が拒否されたら、メッセージの指示に従って直してから、もう一度報告する。`.figma-diff/flow/state.json` は直接書き換えない。

## 画像の読み取り

画像を Read で読み、次を directive の `context.notesPath` のファイルに書く。

- セクションの並びと、各セクションに含まれる要素（見出し・本文・ボタン・カード・アイコンなど）
- 画面上の文言。画像から読める文字はそのまま使う
- 要素の寸法と余白。画像上の px を倍率で割って CSS px に直す
- 色。見た目で読み取った値と、既存トークンのどれに近いか
- 文字の大きさと太さ

写真やイラストは再現しない。同じ寸法の置き換え用の要素で場所を取る。

## 実装

- 既存の共通コンポーネントで作れる要素は、それを使う。
- 色・余白・文字サイズは、読み取った値に最も近い既存トークンを当てる。
- 近いトークンが無い値は、プロジェクトの規約が許す範囲で生値を書き、報告に挙げる。規約で生値が禁じられていれば、最も近いトークンを使って同じく報告に挙げる。
- マークアップ・CSS・スクリプトの規約は、前提チェックで読んだ内容に従う。

## エラーの修正

directive の `context.failures` に、失敗したコマンドと出力の末尾（`tail`）、全文のログ（`logPath`）がある。原因を直す。

## 調整

[references/adjust.md](references/adjust.md) に沿って、差分の大きいところから直す。

## 調整を戻す

直前の調整で差分が減らなかったので、directive の `context.revertTo` 回目の計測をしたときの状態にファイルを戻す。戻したかどうかはファイルの中身で確かめられるので、コミットしてもしなくてもよい。調整の回数が残っていれば、次の directive は調整になるので、同じ原因を避けて別の調整を考える。回数を使い切っていれば、自己レビューに進む。

## 自己レビュー

分岐元との全差分を読み直し、[references/self-review.md](references/self-review.md) の観点で点検する。直したら、もう一度 lint・型チェックを通しておく。

## 報告

`design-flow status` の記録を元に、以下を報告して終了する。各項目は結論だけを 1〜2 行で書く。

- 追加・変更したファイル一覧
- 当てたトークンとコンポーネント、近いトークンが無かった値
- 差分チェックの結果（各回の `diffRatio` の推移と最終の `pass`。打ち切った場合（`gaveUp`）は `compare.png` のパス）
- 画像から読み取れず推測で埋めたところ
